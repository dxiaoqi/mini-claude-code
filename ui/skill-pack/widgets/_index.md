# Widget 目录

| type | 适用场景 | 何时用 |
|---|---|---|
| `markdown` | 文本、解释、列表、代码 | 默认首选，但有上限 |
| `svg` | 图示、流程图、架构图、对比图 | **必须**：流程/架构/关系/时序 |
| `html` | 诊断/练习/镜像/交互演示 | **必须**：交互/表单/动态 |
| `chart` | 数据可视化 | **必须**：数据/对比/分布 |

---

## 分布约束（硬规则）

- **markdown ≤ 总 widget 数的 60%**
- 请求含"流程/架构/关系/时序" → ≥1 svg
- 请求含"交互/表单/动态/demo" → ≥1 html
- 请求含"数据/对比/分布" → ≥1 chart 或 svg

---

## SVG 质量自检

**测试**：把 SVG 里的所有文字去掉，图本身是否还传达关系或流程？

- ✅ 去掉文字后仍有信息（箭头走向表达流程、空间位置表达对比、层级嵌套表达结构）
- ❌ 去掉文字就是几个方块 = 带框的有序列表，用 markdown 能达到同等效果

**合格的 SVG 形式**：两条路径对比、环形循环、层级嵌套、二维坐标映射、空间分区

**不合格**："1→2→3→4→5"五个编号方框横排 = 这不是 SVG，是 markdown 列表

---

## HTML 质量自检

**测试**：用户交互完这个 widget 后，他对概念或对自己的认知是否有变化？

- ✅ **诊断型**：系统反馈"你可能是 X 类型"或"你卡在 Y"
- ✅ **练习型**：用户操作后，系统给出具体的"这样想更接近核心"的反馈
- ✅ **对比型**：用户切换视角，看到同样输入下不同路径的差异
- ❌ **展示型**：把文字换成按钮后面，信息密度等同 markdown
- ❌ **考试型**：只判断对错，不帮理解

**反例**：选完题只显示"正确！"或"错了，答案是 B"  
**正例**：选完题显示"这个选法的典型特征是 X，背后思维是 Y，下次遇到类似情况可以这样想"

---

## 选择决策

1. 先列出请求中的"结构性名词"（流程/架构/数据/交互...）
2. 根据结构性名词决定必须包含的 widget 类型
3. 剩余内容用 markdown 补充，确保不超 60%

## 组合原则

- 一个 phase 内的 widget 应服务于同一个 goal
- "图 + 文说明"组合常见，但文不超过 1 个 markdown
- 避免同一 phase 超过 3 个 widget（考虑拆 phase）
- 不要用多个 markdown 分章节——用一个 markdown 内的 ## 标题分节
