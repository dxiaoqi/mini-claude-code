# 00 · 总览与阅读指南

一套用于复刻并扩展 Claude.ai 流式 artifacts 能力的系统设计文档集。覆盖 skill 约束、渲染运行时、编排层、状态管理、UI 层的完整闭环。

---

## 这套文档是什么

你正在构建一个系统,目标是:
- 用户发出请求,系统产出流式、可交互的 artifact
- Artifact 由多个 widget 组成(markdown / svg / html / chart / ...)
- 生成过程对用户可见("正在思考 → 生成图表 → 继续下一步")
- 产出质量稳定,能应对复杂请求而不陷入"兔子洞"
- 支持迭代编辑("改一下这里"、"加一个图")

这套文档是给 AI 生成代码用的**架构与规范**,不是伪代码也不是最终实现。目标是:读完这套文档,AI(或人)能按规范产出互相配合的代码模块。

## 范围边界(V1 不做什么)

为避免过度设计,以下明确**不在 V1 范围**:

- 多用户并发调度(假设单用户、串行请求)
- 多 tab 的 artifact 实时协作(只做基础状态同步)
- 分布式/高可用架构
- API rate limit 时的自动降级(rate limit 就直接错误提示)
- 国际化、无障碍、版本化策略
- 安全威胁模型(假设可信用户)

这些不是不重要,而是 V1 阶段不值得投入。留给 V2。

## 一些术语的统一定义

| 术语 | 定义 |
|---|---|
| **Artifact** | 一次请求的完整产出,由多个 widget 组成 |
| **Widget** | Artifact 的组成单元,有统一生命周期接口 |
| **Phase** | 生成过程的一个阶段,对应一个可独立评估的用户价值 |
| **Plan** | 由多个 phase 组成的 DAG(V1 仅用线性 plan) |
| **Recipe** | Plan 的骨架模板,根据意图维度匹配 |
| **Milestone** | Phase 结束时的检查点,Critic 在此介入 |
| **Orchestrator** | 管理 plan/phase/critic/budget/HIL 的控制层 |
| **Executor** | 产出内容的模型调用(相对于 Critic) |
| **Critic** | 判断产出是否达标的模型调用(只做判断,不改内容) |
| **HIL** | Human-in-the-loop,系统主动请求用户介入 |
| **ContextBus** | Widget 访问 sendPrompt/tool/state 的统一通道 |

## 如何使用这套文档

**如果你是人类架构师**:按顺序读,在 06 和 07 停下来多想。这两章是系统能不能工作的关键。读完后再回头看 01 的设计哲学,会有新的理解。

**如果你要让 AI 生成代码**:把这套文档全部作为 context 给 AI,指定从 10 的路线图 Step 1 开始,一次实现一个 Step。不要一次性让 AI 生成整个系统——它会在无关紧要的模块里过度发挥,在关键模块里偷懒。

**如果你要扩展这个系统**:先读 01 的设计哲学,判断你的扩展是否违反原则。然后读 02 的模块边界,找到正确的嵌入点。最后读对应模块的具体文档。
