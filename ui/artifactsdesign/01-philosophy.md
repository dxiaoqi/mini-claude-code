# 01 · 设计哲学

这套系统的所有具体设计都派生自以下原则。当后续文档里出现冲突选择,**以本文件为准**。

---

## 核心原则

### 原则 1: 智能感来自系统,不来自模型

"智能感"不来自模型更聪明,来自**系统在正确的时刻问正确的问题**。

纯 agent loop 把"什么时候该停、该换方向、该问人"全交给模型的 token 流判断——这注定不稳定。系统的职责是**外化这些决策点**。

**推论**:
- 意图识别、plan 分解、critic 判断是三个不同调用,不要合并
- 不要相信模型自己说的"我已经做完了",要用外部 acceptance 校验
- 不要让模型自己决定是否触发 HIL,那是 Orchestrator 的权力

---

### 原则 2: 自由度在最内层,控制在最外层

```
外层: 确定性状态机    (阶段 A→B→C 几乎固定)
 ↓
中层: 可变 DAG       (widget 组合由内容决定)
 ↓
内层: Agent 自由发挥  (但被单元 budget 死锁)
```

这是同时获得"灵活"和"稳定"的唯一路径。纯 agent loop 把最外层的控制权也交给了模型,这是它失控的根因。

**推论**:
- Orchestrator 的状态机是硬编码的,不该让模型参与修改
- Phase 之间的切换是确定性的,phase 内部才有自由发挥
- 单个 widget 的内容可以很有创造性,但它的边界、长度、类型是受约束的

---

### 原则 3: Orchestrator 管边界,模型管内容

| Orchestrator 管 | 模型管 |
|---|---|
| Phase 切换 | Widget 里写什么 |
| Budget / 超限判断 | 如何组织语言 |
| 重规划决策 | 如何组织视觉 |
| HIL 触发 | 是否引用前文 |
| 错误恢复策略 | 具体的表达选择 |

两边不越界。越界的后果:
- Orchestrator 越界管内容 → 系统僵硬,产出千篇一律
- 模型越界管边界 → 系统失控,陷入兔子洞

---

### 原则 4: 承认局部失败,不要无限重试

兔子洞的根源是"我还能做得更好"的递归。

**必须允许**:
- Phase 被标记为 `abandoned`,并在产出里注明
- Plan 有未完成的分支,整体仍然交付
- Critic 判断"不够好"时不是无限重试,而是有次数上限,到了就接受现状

**反面教材**:"让我再试一次" → "再试一次" → "再试一次"...

---

### 原则 5: 每个决策点都要回答"成本多少"

Critic 要便宜,HIL 要吝啬,重规划要有预算。**没有成本感知的自主系统一定会失控**。

**每个模型调用都必须有**:
- 最大输入 token
- 最大输出 token
- 超时
- 失败时的 fallback

**每个自主决策都必须有**:
- 触发次数上限
- 累积预算
- 触及预算时的行为定义

---

### 原则 6: 流式体验优先于规划严谨

在"让用户等完整规划完成"和"让用户尽快看到东西"之间,**后者优先**。

这意味着:
- Plan 不等完全展开,就开始执行第一个 phase
- Phase transition 不追求零延迟,但要有视觉上的"思考态"掩护
- Critic 不阻塞主流,异步结果影响下一个 phase 而非当前 phase

这条原则修正了"先完整规划再严格执行"的朴素想法。真实系统里,规划本身就是流式的。

---

### 原则 7: Skill 和 Protocol 是产品接口,不是实现细节

Skill Pack 的写法和 Protocol 的语法,**一旦确定就要稳定**。因为:
- 模型要按这个学习产出
- 渲染器要按这个解析
- 上游工具要按这个集成
- 任何一处改了,全链路都要动

所以:**设计 Skill 和 Protocol 时优先稳定性,宁可多想一层**。不要像 Python 依赖那样随便升级。

---

## 冲突仲裁规则

当两个设计选择冲突时,按以下顺序判断:

1. **用户体验 > 架构优雅**
   例:并行 phase 架构上优雅,但会让流式 UI 错乱,V1 选串行
2. **稳定性 > 性能**
   例:Critic 用同级模型比小模型稳,V1 选同级
3. **简单 > 灵活**
   例:状态机硬编码比配置化简单,V1 选硬编码
4. **明确失败 > 模糊兜底**
   例:超预算直接报错比"尽力而为"清晰,V1 选前者
5. **可观测 > 自动化**
   例:让开发者看到 Critic 的每次判断,比"智能跳过"更重要

---

## 不做什么

几条"看起来该做但实际不要做"的决策,避免后续走弯路:

**不要做**"自动选择最佳 widget"的黑盒。让 Skill 显式声明何时用什么 widget,模型按 skill 选,这样可调试。

**不要做**"自适应 budget"。Budget 要是配置的、显式的、有上下限的。自适应 budget 会变成 Critic 的另一个失控点。

**不要做**"多模型投票"。听起来能提质量,实际上成本翻倍、延迟翻倍、工程复杂度爆炸。提质量靠 skill 的示例和 acceptance 的结构化。

**不要做**"让模型生成 plan 的 JSON schema"。让模型产出结构化的 markdown 标记,代码解析。JSON 在流式场景下半截解析很痛苦。

**不要做**"完全不重试"。有些失败就是模型抽风,重一次就好。重试策略要有,但必须有次数上限。
